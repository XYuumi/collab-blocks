# 07 · 技术选型对比：为什么"原生 DOM"，以及什么时候不该

> 题目问：有没有更成熟的开发框架，而不是原生开发？本文给出三条路线的详细优缺点对比与
> 选择结论。先说结论：**本项目的最优解是"编辑内核保持原生 + 外壳手写轻组件"**；
> 如果目标变为"做一个生产可用的协同产品"，最优解会变成"直接采用 React + TipTap + Yjs
> 全家桶从头实现"，而不是"把本项目迁移过去"——这是两个不同的问题。

## 1. 三条路线

| 路线 | 组成 | 代表产品 |
|---|---|---|
| A. 原生 DOM（本项目） | TypeScript + 手写 DOM 调和 + 自研同步协议 | 本项目 |
| B. 框架外壳 + 原生内核 | React/Vue 管首页/弹窗/状态栏，contenteditable 内核仍是直接 DOM 操作 | 一些中型编辑器 |
| C. 成熟全家桶 | React + **TipTap**（ProseMirror 封装）+ **Yjs**（CRDT）+ y-websocket | 大多数商业协同产品 |

## 2. 逐项对比

### 2.1 contenteditable / 光标 / IME 控制力（协同编辑器的命门）
- **A**：完全控制。每个块一个常驻节点，远端更新只写单个块的 textContent 并保存/恢复光标；
  IME 组词期间不碰该块 DOM。要做到这点必须精确到"哪个节点、哪个属性、什么时机"——
  框架的抽象在这里是负资产（见下）。
- **B**：内核部分与 A 相同；但框架的合并更新（React 18 并发特性/Vue 异步批量）可能与
  "在 composition 期间冻结某个节点"的手工约束打架，需要在 effect 时机上做额外防御。
- **C**：ProseMirror 的文档模型 + View 层本身就是为此设计（state→DOM 的受控映射、
  decoration 系统叠加远端光标/选区），是业界最成熟的答案。
- **结论**：C > A ≥ B。但 A 的控制力对本项目的块模型已经够用且全部代码可读可改。

### 2.2 框架重渲染对编辑器的破坏（A/B/C 的核心差异）
- **A**：不存在该问题。
- **B**：React/Vue 的 key 复用在绝大多数场景没问题，但：同 key 节点属性被 diff 意外回写
  （contentEditable 属性被框架管理）、批量更新与输入事件的竞态、StrictMode 双执行打断 IME——
  每一条都是真实踩过的坑（社区有大量 "contenteditable + React 光标跳变" 的 issue）。
  绕开的代价是 `suppressContentEditableWarning` + 手动 ref 锁定，本质是在框架里模拟 A。
- **C**：TipTap 官方 React/Vue 适配层已解决上述问题（Editor 是命令式的，框架只包壳）。
- **结论**：A、C 安全；B 最尴尬——两套心智并存，坑最多。

### 2.3 协同同步层（本项目的核心价值）
- **A**：自研协议（版本 + 块级 CAS + 事务幂等 + 微型变换 + 对账重放）。这正是面试作品
  要展示的东西：每个决策都有 docs 与测试。换 B/C 不改变这层（协议与 UI 无关），
  换 Yjs 则等于放弃自研（见 2.6）。
- **C**：Yjs（YATA CRDT）+ y-websocket：开箱即用的离线合并、任意拓扑收敛、
  awareness 协议（光标/在线状态现成）。成熟度碾压自研，但它是**另一套一致性哲学**
  （无服务器权威、最终一致），服务端无法做仲裁型功能（如本文档的强制块锁按作者拒绝、
  doc.replace 的"后做生效"）——CRDT 里没有"拒绝"这个动作。
- **结论**：产品化选 Yjs（省 80% 协议层工作量）；本项目必须自研（题目就是问协议怎么设计）。

### 2.4 UI 外壳的开发效率
- **A**：首页/弹窗/状态栏手写 DOM——本项目约 500 行外壳代码，可承受；但状态再复杂
  （协作者面板、评论流、权限管理页）会线性变痛苦。
- **B/C**：声明式 UI 在表单/列表/弹窗上效率明显更高，生态组件库可用。
- **结论**：产品做大 → 框架外壳收益递增；本项目体量 → 手写成本可控且零构建负担。

### 2.5 包体积与依赖面
- **A**：构建产物 ~62KB（gzip ~19KB），运行时零依赖（ws/express 在服务端）。
- **B**：+react/vue 运行时（~45KB gzip 起）。
- **C**：+react+tipTap+yjs ≈ 300KB+ gzip 量级，依赖树数十个包。
- **结论**：A 显著最小；演示/面试场景加载即所得。

### 2.6 可测试性与可调试性
- **A**：客户端模型是纯函数（无 DOM 依赖），能做双模型收敛测试（本项目 9 个）；
  全链路无框架黑盒，任何行为都能沿代码路径解释。
- **C**：ProseMirror/Yjs 自身测试极充分，但你的自定义行为的调试要深入两套大型抽象。
- **结论**：A 对"理解与讲解"最优；C 对"稳定交付"最优。

### 2.7 生产适配性（真实产品视角）
- **A**：所有问题都要自己解决（本项目的锁/权限/重连/对账已是其中一小部分），
  长尾坑（safari 选区怪癖、超大文档性能、移动端 IME）无人兜底。
- **C**：ProseMirror 十年生态（表格/评论/协同光标/移动端修复全有），是商业产品的合理默认。
- **结论**：真要做产品，选 C 并接受其哲学（CRDT/无服务器仲裁），不要在自研协议上
  硬堆产品功能。

## 3. 结论

| 场景 | 最优解 |
|---|---|
| **本项目**（展示协同原理的面试作品） | **A：原生 DOM + 自研协议**。编辑内核必须精确操作 DOM；协议是价值主体；62KB 产物即开即用 |
| 中型内部工具（要快速堆 UI） | B 的变体：TipTap + Vue/React，协议仍可用自研（op 走 socket） |
| 商业协同产品 | C：React + TipTap + Yjs 全家桶**从头建**，而非迁移本项目——一致性哲学不同，迁移是伪命题 |

**一句话**：框架解决的是"UI 状态同步"问题，而协同编辑器的难点恰恰在"不能让任何人
自作主张地同步 UI"——所以内核用框架是逆水行舟，外壳用框架是锦上添花，
本项目的外壳复杂度还没到需要锦上添花的程度。
