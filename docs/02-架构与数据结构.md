# 02 · 架构与数据结构

## 1. 总体架构

```
┌────────────────────────── 浏览器 A ──────────────────────────┐
│  Editor(DOM 渲染/输入捕获/手势)                               │
│    ↓ ops                                                     │
│  DocModel(可见状态 = 服务器文本 ⊕ 未确认本地 ops + 微型变换)     │
│    ↓ Tx                                                      │
│  TxQueue(合批/发送/超时重发/ACK/NACK 修复)                     │
│    ↓ WebSocket                                               │
└───────────────────────────┬──────────────────────────────────┘
                            │  hello / tx / ack / nack / remote.op
                            │  cursor / lock.* / sync / config
┌───────────────────────────┴──────────────────────────────────┐
│  Hub(会话/presence/块锁 TTL/广播)                              │
│    ↓ submit(tx)                                              │
│  DocEngine(幂等去重 → 锁检查 → 块级 CAS → 原子应用 → 版本+1)     │
│    ↓                                                          │
│  Persistence(doc.json + 每50版本快照)                          │
└──────────────────────────────────────────────────────────────┘
```

**单一权威模型**：服务器是文档状态的唯一真相源（Source of Truth）。客户端持有
"服务器文本 + 自己未确认操作"的乐观视图；一切分歧由服务器的确定性规则裁决，
客户端被拒绝后按服务器权威状态修复重试。这是放弃 OT/CRDT 之后保证收敛的根基。

## 2. 技术选型与理由

| 层 | 选择 | 为什么 |
|---|---|---|
| 前端 | TypeScript + Vite + **原生 DOM（无 React/Vue）** | contenteditable 的光标/选区/IME 状态活在 DOM 里，框架重渲染（即使是 keyed diff）也可能销毁重建节点导致光标丢失、输入法中断。本项目的渲染单位是"块级精确更新"：远端修改只写单个块的 textContent 并保存/恢复光标，结构修改按 data-id 复用节点移动——这些需要直接操作 DOM 才能做对。同时，手写调和逻辑最能体现对协同渲染机制的理解 |
| 编辑模型 | **每 Block 一个 contenteditable**（`plaintext-only`） | 把 contenteditable 的"偏移混乱"隔离在块内；块间顺序由自己的数据模型管理，天然支持按块加锁/按块同步/按块冲突检测（Notion 的思路） |
| 输入捕获 | `input` 事件后对新旧文本做**前后缀 diff** 推导 op | 不劫持 beforeinput/keydown，保留原生行为（输入法、自动更正、选区替换）；diff 一次就能得到"insert 或 delete"的最小操作 |
| 后端 | Node.js + `ws` + Express，单端口 | WebSocket 与 HTTP 同进程同端口，部署即一个命令；Node 事件循环天然适合"单文档内串行仲裁 + 多连接按房间广播"模型（v3 起多文档 = 多引擎懒加载） |
| 数据库 | **SQLite（node:sqlite，Node 内置）** | 用户/会话需要唯一约束与 token 反查（文件做不到）；文档需要"每次提交即落盘"（文件防抖有丢失窗口）；SQLite 单文件零运维。选 node:sqlite 而非 better-sqlite3：零原生依赖（Windows/CI 免编译），API 同构可平滑替换 |
| 认证 | scrypt 加盐哈希 + 随机会话 token | 不引 JWT 库：会话表可撤销、免签名密钥管理；`crypto.timingSafeEqual` 常数时间比对防时序侧信道 |
| 持久化 | 每次提交事务写 SQLite + 每 50 版本快照 | 提交即落盘消除崩溃丢失窗口（有重启一致性测试） |
| 测试 | node:test + tsx | 引擎/协议/认证/存储单测与集成；客户端模型是纯逻辑（无 DOM 依赖），可做**双模型收敛测试** |

## 3. 数据结构

### 3.1 文档与块（共享契约 `shared/protocol.ts`）

```ts
DocSnapshot = {
  docId: string
  version: number          // 文档版本，每个成功事务 +1，单调递增
  structureVersion: number // 结构版本，任何块增删 +1
  blocks: Block[]          // 有序块数组
}

Block = {
  id: string     // 服务器/客户端生成的 UUID —— 全局唯一、幂等重发不产生重复块
  type: BlockType // "text" | "h1" | "h2" | "h3" | "bullet" | "todo" | "code"
  text: string   // 块内纯文本
  checked?: boolean // todo 块的勾选状态
}

// 服务器内部块（不下发客户端）：
SrvBlock = Block + {
  blockVersion: number  // 该块最后一次被修改时的文档版本 —— 块级 CAS 的依据
  lastWriter: string    // 最后写入者 —— "同作者连续写豁免"的依据
}
```

**为什么 Document-Block 两级模型**（完整论证见 docs/05 Q2）：
- 块是天然的**最小同步单元**：一次编辑几乎总是落在一个块内，diff 和 op 都小；
- 块是天然的**最小冲突单元**：两个人改不同的块永远不冲突（块级 CAS 放行），
  只有同块并发才需要仲裁——冲突域从"整篇文档"缩小到"一个段落"；
- 块是天然的**最小加锁单元**：锁一个段落而不是整篇文档，并发度最高；
- 块有稳定 ID：操作锚定、光标定位、远程渲染、Undo 都按 ID 寻址；
- 扩展性：块的 type 字段为富文本/嵌套留了口子。

**为什么不是三级（Block-行-字符）或一级（整篇纯文本）**：
一级文本（如纯 textarea + 整篇 diff）实现最简单，但任何编辑都是"整篇"的修改，
无法做块级冲突隔离、无法加锁、远程渲染要整篇重写光标全丢；
三级则复杂度上升而收益递减（行不是用户心智模型中的编辑单位，段落才是）。

### 3.2 操作 Op（原子操作，全部以 BlockId 锚定）

```ts
{ type: "block.insert", id, afterId: string | null, text, blockType? }  // 插到某块之后；null=末尾
{ type: "block.delete", id, text?, prevId?, blockType?, checked? }      // * 为 Undo 反演上下文
{ type: "block.update", id, blockType?, prevBlockType?, checked?, prevChecked? } // 类型/勾选变更，参与块级 CAS
{ type: "text.insert", blockId, offset, text }
{ type: "text.delete", blockId, offset, length, text? }                 // text 为被删文本（Undo 用）
```

设计要点：
- **锚定用 ID 不用数组下标**：并发结构变更时下标会漂移（"在第 3 块后插入"在别人删了
  第 2 块后就错了），ID 锚定天然免疫；锚点块被并发删除时服务器**宽松重锚**
  （退化为追加到末尾），客户端同步重锚——两端语义一致。
- `text.delete` 携带被删文本、`block.delete` 携带文本与前块 ID：这是**物化的逆操作
  上下文**，Undo/本地回滚不需要再去查历史状态。

### 3.3 事务 Tx（同步/重试/幂等的基本单位）

```ts
Tx = {
  txId: string        // 客户端生成的 UUID —— 服务器幂等去重依据
  docId: string
  baseVersion: number // 客户端提交时所知的文档版本 —— 服务器块级 CAS 的输入
  author: string
  ts: number
  ops: Op[]           // 一段时间内的编辑合批（约30ms）或一次结构手势的全部 op
}
```

**为什么需要事务**：回车拆块 = `text.delete(尾)` + `block.insert(新块)` 两个 op，
必须原子：要么都生效要么都不生效，否则网络重试/冲突回滚会出现"尾巴删了但新块没建"
的中间态。Undo/Redo 也以事务为单位求逆。合批（30ms）则把连续键入合并为一个事务，
减少版本膨胀与广播量。

### 3.4 客户端模型（`client/src/model.ts`，核心）

```
可见状态 blocks    = serverText ⊕ pending(按提交顺序折叠)
serverText: Map<blockId, string>   // 我已知的每块服务器权威文本
pending:   PendingTx[]             // 未确认的本地事务
```

三类事件推进 serverText：
1. `remote.op`（他人提交）→ 应用到 serverText + 对我 pending 中同块 op 做**块内微型变换**（偏移平移）；
2. `ack`（自己提交确认）→ 用"发送时的 ops"推进 serverText，可见文本不变（早已乐观显示）；
3. `snapshot`（重连对账）→ 整体重置为服务器快照，重放未确认 pending。

修复管线（NACK 冲突 / 重连共用）：**回滚全部 pending（逆序反演）→ 覆盖权威文本 →
修正（clamp/重锚）→ 顺序重放 → 以当前版本为基线重发（同 txId）**。

## 5. 关键不变量（Invariants）

1. **权威性**：服务器 doc 是唯一真相；客户端任何本地状态最终都会被
   ack/nack/snapshot 收敛到与服务器一致。
2. **版本单调**：version 只在服务器递增；客户端只接收（ack/remote.op/snapshot 三通道，值一致）。
3. **幂等**：同一 txId 重复提交，服务器只执行一次（仅缓存成功结果；nack 不缓存，重发重新评估）。
4. **事务原子**：一个 Tx 的 ops 要么全部应用要么全部不应用（副本上应用，成功才换入）。
5. **折叠等价**（收敛的根源）：`可见文本 == fold(该块全部 pending 文本 op, serverText)`，
   且在 ack 时刻 serverText 恰等于"我发送 ops 的应用基底"（由块级 CAS 保证没有
   他人写入穿插），因此服务器应用结果与本地折叠逐字符一致——`client/test/model.test.ts` 验证。
