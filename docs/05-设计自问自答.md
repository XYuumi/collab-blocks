# 05 · 设计自问自答（含思考过程）

> 本文以"自己提问自己答"的方式记录关键设计决策的完整思考过程：考虑过什么、
> 否决了什么、为什么这么选。协议与机制细节见 docs/02-04。

---

## Q1. 为什么会选择这个数据结构？

**选型**：`Document → Block[] → text` 两级结构，操作模型是 4 种原语 Op
（block.insert / block.delete / text.insert / text.delete）+ 事务 Tx，服务器块上带
`blockVersion`（块级 CAS 依据）与 `lastWriter`（同作者豁免）。

**思考过程**：先列出候选再逐一对照需求。

1. **整篇纯文本 + 全量 diff**（类 textarea）：实现最快，但 (a) 每次同步传输整篇，
   带宽与 diff 开销随文档增大；(b) 无法定位"谁改了哪里"，任何两人并发都是整篇冲突；
   (c) 远程渲染要整篇重写，光标必丢。否决。
2. **字符级操作日志**（OT 系）：粒度最细、合并能力最强，但变换正确性极难保证，
   且题目要求思考"不用 OT"的方案。作为 docs/04 的演进路线保留。
3. **块结构 + 块内文本**（Notion 系）：编辑的心智单位是"段落"，冲突单位、加锁单位、
   同步单位、渲染单位天然对齐到块；块内纯文本让 diff/op 极简；块有稳定 ID，
   一切寻址（操作锚定、光标、远程渲染、Undo）都按 ID 而非位置。**选定**。

数据结构上的几个关键决定：
- **Op 用 afterId 锚定而不是数组下标**：下标在并发下会漂移（别人删了前面的块，
  我的"插到第 3 块后"就错了），ID 锚定免疫这个问题；锚点被并发删除时宽松重锚到末尾
  （两端语义一致，有测试）。
- **每个块带 blockVersion 而不是只有文档 version**：文档级版本做 CAS 意味着"任何
  两人并发必冲突"；细化到块后"不同块并发永不冲突"——这是不用 OT 还能高并发协同的关键。
- **text.delete 携带被删文本、block.delete 携带文本与前块 ID**：逆操作在创建时就
  物化，Undo/回滚不需要查历史。
- **服务器与客户端共享一份协议定义**（shared/protocol.ts）：契约漂移是协同 bug
  的头号来源，类型共享让前后端在编译期对齐。

## Q2. 为什么是 Document-Block，或者为什么不是？

**是**，理由见 Q1.3。再补两条"为什么不是别的层级"：

- **为什么不是 Document 一级**：等价于候选 1，冲突域 = 整篇，否决。
- **为什么不是 Document-Block-行-字符 三级**：行不是用户心智中的编辑单位
  （段落才是）；行号/行 ID 的维护成本与块相当但收益更小（块内本来就小，
  很少需要行级仲裁）；层级越多，结构 op 的变换/回滚越复杂。行级信息
  （视觉换行）交给 CSS，不进数据模型。
- **什么时候会需要第三级**：如果块内要做富文本（粗体/链接跨字符样式），就需要
  块内再分 span/字符标记——那是引入 CRDT（如 Peritext 类方案）的信号。本项目
  Block.type 预留了扩展口。

反向问题"Block 模型的代价"：(a) 回车/合块等手势要拆成多 op 事务，正确性要求高
（已用事务原子性解决）；(b) 块内文本很长时（粘贴一大段），一次 op 很大——
可接受，因为冲突粒度并没有变差（仍是这个块）。

## Q3. 两个人同时修改怎么办？最终内容是什么？为什么？

分三种情况（机制见 docs/04，这里给结论与理由）：

1. **同时改不同的块**：两人都成功。最终内容 = 两处修改都在。
   为什么：块级 CAS 发现各自目标块的 blockVersion ≤ 我的 baseVersion（对方没动过
   我的块），放行。版本号串行 +1，双方都收到对方的 remote.op。

2. **同时改同一个块、提交有先后**（最常见，比如都盯着同一段话打字）：
   先提交者成功；后提交者的事务被 CAS 拒绝（CONFLICT + 服务器附该块权威文本）。
   **但后提交者的输入不会丢**：客户端早在他提交前收到过先提交者的 remote.op，
   已经把自己的 pending ops 做了"块内微型变换"（把偏移平移过对方的插入/删除），
   所以被拒后修复管线重放的就是**合并后的操作**，重试成功。
   最终内容 = 两人在该块的输入都保留，字符顺序按"先提交者在前"的确定性平局规则。
   例（有自动化测试）：A、B 都在 `"hello"` 开头插入，A 的 "A" 先落地 → 最终
   `"ABhello"`。

3. **同时改同一个块、离线窗口内**（B 断线时编辑，A 也在编辑）：B 重连对账以快照
   （含 A 的修改）为基底重放自己的 ops：若 A 动过同一块，B 的重放事务会被 CAS 拒 →
   B 再走修复管线合并重试。结果同 2。

**为什么敢保证"最终内容"**：服务器是单一权威且全序串行；客户端可见状态满足
"折叠等价"（可见文本 = 服务器文本 ⊕ 我的未确认 ops）；ack 的不变量（应用基底 ==
我的 serverText）保证服务器应用结果与本地折叠逐字符一致。收敛性由
`client/test/model.test.ts` 的双模型测试验证（含全部上述场景）。

**平局规则为什么"先提交者在前"**：变换时 `offset ≥ ro → +=len`，同位置并发插入
后到者的偏移被推后一位。规则本身任意但必须**确定且两端一致**（否则不收敛）。
选中"先提交在前"是因为它与服务器的提交顺序一致，直觉上"先说的在前"。

## Q4. 网络断开怎么办？

现象与处理链路：
1. WebSocket close 事件 → 状态栏变红"已断开"，顶部横幅提示"编辑已保留在本地"；
2. **乐观更新继续工作**：所有编辑照常进入模型 pending，只是不发送
   （"待同步 N"计数持续增长）；
3. 指数退避重连（0.5s→1s→2s…上限 8s，加随机抖动防止大量客户端同时重连打爆服务器）；
4. 重连成功 → `sync {haveVersion, pendingTxIds}` 对账 → 服务器回全量快照 +
   "已执行过的 txId 集合" → 客户端以快照重建、重放未确认事务、逐个补发；
5. 补发被拒（对端在断线窗口改了同一块）→ 修复管线合并重试（同 Q3.2/3.3）。

设计要点：
- **为什么重连要全量快照而不是增量 op log**：省去服务器保留历史 op 与客户端
  补洞的逻辑，复杂度低一个量级；文档体积小（百个块）时传输代价可忽略。
  文档大了的优化方案见 docs/04 演进路线（op log / 分块拉取）。
- **为什么心跳**：TCP 半开连接（对端消失但没发 FIN）无法靠 send 失败发现；
  应用层 ping 5s + 服务器 15s 超时剔除，让"假在线"窗口有界。
- 期间对端看到该用户离线（presence 剔除），其远程光标淡出。

## Q5. 如果修改本地已经显示，WebSocket 断了，服务器没收到，你会怎么办？

这正是乐观更新的本质代价：**本地显示 ≠ 已持久化**。我的处理分三层：

1. **显示层如实反映状态**：状态栏"待同步 N"在断线期间持续 >0，横幅明示
   "编辑保留在本地，重连后自动同步"。用户能感知"还没同步"，不会误以为已保存。
   （这层看似简单，却是最容易被忽略的——静默的乐观更新等于撒谎。）

2. **数据层不丢**：未确认事务在模型 pending 里保活；掉线重发由重连对账统一处理
   （Q4.4），同一 txId 保证不重复执行。

3. **诚实的边界**：如果用户在断线期间**关闭页面**，内存中的 pending 随之丢失
   （本项目接受这个限制并如实写在文档里；改进方案是 pending 落 localStorage，
   重开页面后对账补发——为什么不默认做：引入"陈旧本地存储与服务器状态冲突"的
   新问题域，收益/复杂度比不划算，见 docs/04 已知限制）。

另外两个相关细节：
- 在线但 **ack 超时**（5s）≠ 断线：先同 txId 重发（最多 5 次），不触发对账
  （对账比单事务重发贵得多）；
- 发送成功但 **ack 丢失**：重连对账时服务器回告该 txId 已执行（ackedTxIds），
  客户端把它从 pending 剔除——不重复应用。

## Q6. 重复发送怎么办？

重复可能来自三个层面，分别处理：

| 层面 | 机制 |
|---|---|
| **传输层**：WS 消息重复到达 | TCP 下去除重是不必要的；TCP 保证字节流不重复 |
| **应用层**：客户端超时重发 / 重连补发 | **txId 幂等**：服务器 `txId → 结果版本` 缓存，重复事务直接返回缓存 ack，不执行 |
| **结构层**：block.insert 重放时块已存在 | 服务器按 op 语义幂等：目标 id 已存在 → 跳过该 op |

幂等缓存的两个关键决定：
- **只缓存成功结果，不缓存 nack**：nack 的语义是"未执行"；重发必须重新评估
  （服务器/他人状态可能已变化，上次拒绝不代表这次也拒绝）。
- **客户端重发永远沿用原 txId**：这样"已执行但 ack 丢失"的事务会被缓存命中，
  返回当时的版本号，客户端状态机回到正轨。
- 缓存容量 5000 条 FIFO：覆盖合理的重发窗口与重连对账窗口，不无限增长。

## Q7. 客户端因超时重发 Tx、没收到 ACK 又重发，服务器怎么避免执行两次？

完整时序推演（这是 Q6 的最坏情况组合）：

```
T0  C → S: tx {txId: X, baseVersion: V, ops}
T1  S:    执行成功，version → V+1，进入幂等缓存 {X: V+1}
T2  S → C: ack {X, V+1}          ← 这个 ack 在网络中丢失/延迟
T3  C:    5s 超时，判定未确认 → 重发 tx {txId: X, ...}   （同 txId！）
T4  S:    幂等缓存命中 X → 直接返回 {ack, V+1}，不重复执行
```

**为什么 T4 一定不会重复执行**：服务器对每个 txId 只做一次"评估-应用"，
成功即缓存结果版本；之后任何同 txId 的到达都短路返回缓存。应用与缓存写入在
同一个同步代码块内完成（Node 单线程，无并发窗口）。

**为什么客户端重发的一定是同 txId**：TxQueue 的超时重发与重连补发都用
`pending` 中的原事务（txId 不变）；被 nack 拒绝后修复管线重建的 ops 虽有变换，
但仍沿用原 txId——此时原事务**必然未被服务器执行**（nack 语义保证），不存在
"服务器应用了旧版本 ops 而客户端状态是变换版"的分歧；若服务器其实已执行
（说明客户端收到的是过期的 nack，正常流程不可能出现），重发会命中缓存返回 ack，
客户端以其推进版本，状态收敛。

**边界情况：重连后重建的 ops 与服务器已执行的原始 ops 不同怎么办？**
重建只改动"受影响"的 op（目标块被他人改过 → 原始 op 必被拒/未执行；
未受影响 → 重建后与原始逐字节相同）。因此"已执行"与"已重建"不可能同时发生在
同一个 op 上。这是重发沿用 txId 的安全性论证，也是幂等缓存不存 ops 内容、
只存结果版本的原因（服务器不需要比对内容，txId 即身份）。

## Q8. 如果不用 OT/CRDT 怎么办？

**我的组合拳：Version + 块级 CAS + Reject + 自动 Retry + （可选）Block Lock，
再加一层"块内微型变换"改善合并体验。** 逐一说明为什么是它们、不是别的：

### 8.1 各手段的思考

- **Version（版本号）**：一切乐观并发控制的基座。没有版本就无法定义"我基于哪个
  状态做的修改"，也就无法检测冲突。成本：一个整数。
- **CAS（Compare-And-Swap，校验 baseVersion 与块状态）**：把"冲突检测"从模糊的
  diff 变成精确的谓词。关键是**把 CAS 粒度做到块级**：文档级 CAS 下两人并发几乎
  必冲突（任何修改都 bump 文档版本），块级后只有真正同块并发才冲突——
  这一步决定了"不用 OT 也能好用"。
- **First-Write-Wins（FWW）**：后到者直接丢弃。实现最简单，但**静默丢数据**。
  对"两人同时在不同位置加字"这种本可合并的场景也丢弃，浪费。仅适合显式锁定模型。
- **Last-Write-Wins（LWW）**：后写覆盖。**静默回滚先写者的数据**，比 FWW 更危险
  （丢失的是"已被服务器确认过"的内容）。适合无合并语义的字段（如用户昵称），
  不适合文本内容。
- **Reject（拒绝）**：不丢数据、不执行错误操作，把"怎么办"交给信息最全的一方
  （客户端知道自己用户的意图）。缺点是用户可能看到失败——所以必须配 Retry。
- **Retry（重试）**：光 Retry 不修正 ops 就是"撞墙循环"（服务器状态已变，
  旧 ops 永远被拒）。正确姿势是**先基于服务器权威状态重建（变换/clamp/重锚），
  再重试**——这也是本方案里"微型变换"的用武之地。
- **Block Lock（块锁）**：把冲突从"事后仲裁"提前到"事前预防"。锁粒度小（段落），
  TTL + 续期 + 断连释放避免僵死。**为什么不是 Document Lock**：文档锁并发度为 1，
  "协同"退化成"轮流编辑"。本项目把块锁做成两种模式：咨询式（默认，只提示不阻止，
  保留无锁冲突处理的完整路径）与强制式（服务器拒绝写入，适合强约束场景），
  顶栏可切换——两 种模式都能演示，方便对比。

### 8.2 组合后的行为（映射到 Q3）

```
不同块并发 ──── CAS 放行 ────→ 双双成功
同块并发   ──── CAS 拒绝 ──┬→ 微型变换合并 → Retry → 成功（输入都保留）
                          └→ 仍冲突（罕见）→ 丢弃并明确告知（绝不静默）
同块强约束 ──── Block Lock → 事前就不允许并发
```

### 8.3 为什么这个组合"够用且正确"

正确性不依赖变换的巧妙，只依赖三件事：(1) 服务器串行仲裁（全序）；
(2) 事务幂等（txId）；(3) 客户端被拒后**以服务器权威状态为基底重建**。
微型变换只决定"合并得好不好看"，不决定"收不收敛"——这是与 OT 的本质区别：
OT 里变换函数错了系统就不收敛；这里变换错了最多丢一次重试机会，最终仍被
CAS/快照对账拉回一致。**把"好看"与"正确"解耦，是这套方案最核心的工程取舍。**

## 其他自问自答（开发中真实遇到/想到的问题）

### Q9. 为什么每块一个 contenteditable，而不是整篇一个？
整篇 contenteditable 里浏览器会自由产生 div/br/text 混合结构，光标偏移和
"块边界"都要靠猜。每块一个 CE 把"块内编辑"完全交给浏览器、"块间结构"完全交给
自己，职责清晰。代价是跨块手势（方向键、合并）要自己实现——这些逻辑本来就需要
协议层感知，不算额外成本。

### Q10. 为什么用 input 后 diff，而不是劫持 beforeinput？
劫持 beforeinput + preventDefault 要自己实现所有编辑行为（包括 IME），中文输入
基本没法保证正确。diff 方案保留 100% 原生行为（含输入法、选区替换、自动更正），
30ms 合批把碎片化 input 合成事务。IME 组词期间不重写该块 DOM（避免打断组词），
compositionend 后统一 diff。

### Q11. 为什么合批窗口是 30ms？
键入间隔通常 80-300ms，30ms 足以合并"连击"又不会让用户感知延迟（人对 100ms 内
的反馈无感）。更大的窗口（如 500ms）会让一次事务包含用户已经"改主意"的内容，
撤销粒度也变差。

### Q12. 锁为什么要 TTL？没有 TTL 会怎样？
客户端崩溃/断电/杀进程时不会发 release，锁就永远卡住（"僵死锁"）。TTL 15s +
持锁者每 5s 续期：正常使用无感，异常退出最多 15s 自愈。这是所有租约型分布式锁
的标准做法（etcd lease、Redis SET NX EX 同理）。

### Q13. Undo 为什么是"逆操作事务"而不是"状态快照回退"？
(1) 状态快照回退会把**别人的修改**一起回退（不可接受）；(2) 逆操作天然只作用于
我自己改过的内容；(3) 逆操作作为一个普通 Tx 提交，自动获得同步、冲突处理、
幂等全套能力——不需要为 Undo 单独设计协议。代价：逆 op 撞上他人同块修改会被
拒绝/偏移（已知限制，docs/04）。

### Q14. 服务器崩溃会丢多少数据？怎么改进？
防抖 200ms 落盘 + SIGINT 兜底，硬杀最多丢最后 200ms 内的提交。改进路线：
(1) 提交日志（WAL）：每次提交 append JSONL，重启重放——最多丢 0 条；
(2) 每事务 fsync —— 延迟换持久性；(3) 定期快照 + 日志截断控制重放长度。
本项目选防抖落盘是工程上的折中，文档如实标注。

### Q15. 为什么消息里 author 以服务器会话为准，不信任客户端字段？
否则任何客户端可伪造他人 author，绕过"同作者豁免"与锁检查。服务器用连接绑定的
会话身份覆盖 Tx.author（server/src/hub.ts）。这是最小权限原则在协议上的体现。

### Q16. structureVersion 有什么用？
结构 CAS 的辅助：`block.insert/delete` 不触碰任何已有块的文本，单独靠 blockVersion
检测不到结构并发。本项目对结构并发选择了"宽松重锚"（锚点没了就追加末尾），
structureVersion 目前主要用于诊断与未来更严格的结构 CAS 预留。

### Q17. 两个标签页算两个用户吗？
算。身份存 sessionStorage（按标签页隔离）而非 localStorage（按域名共享），
开两个标签页即是两个用户、两种颜色——这是刻意的演示友好设计。

## v2 新增问题（用户系统 / 数据库 / 块类型 / 安全加固）

### Q19. 为什么选 SQLite？为什么用 node:sqlite 而不是 better-sqlite3 / MySQL？
需求三件事决定了必须是数据库：(1) 用户名唯一约束与查询（文件做不了唯一性）；
(2) 会话 token 反查；(3) "每次提交即落盘"消除崩溃丢失窗口——v1 的 JSON 防抖写有 200ms 窗口，
而写入频率是每次键入合批（高频小事务），正是 SQLite 的甜点区。
选 node:sqlite：Node 24 内置、零原生依赖（Windows/CI 免编译踩坑）、API 与 better-sqlite3
同构（可平滑替换）；单文件 data/collab.db + WAL 模式。不选 MySQL/PG：单机演示杀鸡用牛刀，
还要额外部署。

### Q20. 登录态为什么存 sessionStorage（按标签页）而不是 localStorage（按域名）？
刻意的取舍：本项目的核心演示场景是"同一浏览器两个标签页 = 两个协作用户"。
localStorage 会让两个标签页共享同一登录态变成同一个用户，演示就废了；
sessionStorage 天然按标签页隔离，且刷新不丢——满足"双开演示"与"登录持续"两个需求。
多账号多窗口协作的真实产品用 localStorage + 显式账号切换器（记在 docs/06 残留风险）。

### Q21. 用户名重复判断是怎么做的？为什么大小写不敏感？
三层：表结构 `username TEXT UNIQUE COLLATE NOCASE`（数据库兜底，并发下也不会重）→
写入前预检查（返回友好错误"已被占用"而不是裸 UNIQUE 异常）→ HTTP 400 带明确文案。
大小写不敏感是因为用户心智中"小明"和"XiaoMing"式的英文大小写变体不算不同名字
（防"仿冒"：大小写不同但视觉相同的名字会让 presence/光标显示产生冒充歧义）。
访客名同样走唯一性分配（冲突随机后缀重试，最多 50 次）。

### Q22. 密码为什么不 bcrypt 而是 scrypt？token 为什么放数据库而不是 JWT？
scrypt 是 Node 内置（零依赖），抗 GPU/ASIC 的内存困难哈希，安全性与 bcrypt 同级；
bcrypt 需要原生依赖。token 放 sessions 表：(1) 登出即删、立即可撤销（JWT 要等过期）；
(2) 无需管理签名密钥；(3) 演示项目单机部署，无跨服务校验需求。代价是每次 hello 查一次库——
SQLite 单行主键查询微秒级，可忽略。

### Q23. 块类型（标题/列表/待办/代码）是怎么参与协同与冲突处理的？
新增 `block.update {id, blockType?, checked?}` op：**与文本操作完全同权地参与块级 CAS**
（目标块存在性检查 → 锁检查 → blockVersion/lastWriter CAS → 应用 → 推进块版本）。
客户端在 remote.op 中把它当作结构事件（重建该块 DOM 节点，保留光标）；Undo 逆操作
物化在 op 里（prevBlockType/prevChecked）。被拒后的重放语义：属性变更没有可变换的偏移，
重放即"后意图生效"（三方收敛，有模型测试）——这等价于把 LWW 限制在了"重试成功"这个
明确的、可见的路径上，而不是静默覆盖。

### Q24. "/"菜单为什么在输入层实现而不是按钮工具栏？
菜单要出现在光标处（上下文就是正在编辑的块），输入层实现（text === "/" 触发、
后续输入过滤、↑↓/Enter/Esc 键盘导航）与编辑器手势共用同一套事务管线——选择类型 =
`text.delete("/") + block.update` 两笔 op 的原子事务，天然可撤销、可同步、可冲突处理。
工具栏版本做不到"就地转换当前块"的直觉性。Markdown 触发（`# `/`- `/`[ ] `/```` ``` ````）
同理复用该管线，且行首独占锚定保证不会误伤正文中的符号。

## v3 新增问题（多文档 / 分享链接 / 权限 / 恢复）

### Q25. 多文档怎么做的？两个文档的人会不会互相看到？
WS 连接绑定单一文档（hello 携带 docId），Hub 里每条会话记录所属文档，
presence/光标/块锁/广播全部先按 docId 过滤再发（锁表键为 `${docId}:${blockId}`）。
引擎按文档懒加载（DocManager，LRU 上限 64 个活跃引擎；每次提交已同步落盘，
淘汰只是释放内存，重新访问时从 SQLite 重载）。有专门的房间隔离测试：
文档 1 的提交与 presence 不会出现在文档 2 的会话里。

### Q26. 分享链接的权限模型为什么这样设计？"UUID 即凭据"安全吗？
三种角色（owner/editor/viewer）由三件事决定：进入方式（/d 编辑链接 vs /r 只读令牌）、
文档归属（owner_id）、"仅创建者可编辑"开关。viewer 的一切写路径在**服务器侧**拒绝
（客户端只读只是体验优化，不是安全边界）。
"编辑链接 = 知道 docId（UUID）即可编辑"是刻意的产品取舍（未加密腾讯文档/石墨同理）：
UUID 128 位不可枚举，链接本身就是凭据；只读令牌（ro_token）是第二把独立的钥匙。
真正要防"链接转发后失控"需要协作者名单模型（每人单独授权），那是账号体系的下一步，
本项目的开关（enforceOwnerEdit）是它的最小可用近似。

### Q27. 快照恢复为什么用 doc.replace 事务，而不是服务器直接覆盖或客户端逐块回放？
三种方案：(a) 服务器直接覆盖——绕过了事务管线：无版本推进语义、无广播协议位、
不可撤销、客户端不知道如何把 pending 重放到新状态；(b) 客户端逐块算 diff 回放——
块多时是 O(n) 个事务、非原子（中途断线产生混合态）；(c) `doc.replace` 单事务——
原子提交、走既有 ack/广播/幂等管线、**逆操作物化（prevBlocks）使其可撤销**、
他人端收到后"serverText 重置 + 自己 pending 重放"（复用重连对账的重放机制）。
代价是单事务负载大（上限 2000 块/400K 字符防护），但恢复是低频显式动作，可接受。

### Q28. pending 为什么选"localStorage + 对账重放"而不是"离线优先（offline-first）"？
目标只是"关页/崩溃不丢未确认编辑"，不是"长期离线编辑"：
- 存储按 `ce-pending-<docId>` 隔离，防抖 500ms 写入，上限 256KB / 7 天；
- 重开页面后走**既有**的 sync 对账：服务器回告 ackedTxIds（哪些其实已提交），
  客户端剔除后重放补发——没有为"关页恢复"新增任何一致性机制，全部复用重连管线；
- 真正的离线优先（长时间离线、多端合并）需要操作日志 + 因果版本（或 CRDT），
  与本项目的"服务器权威 + 块级 CAS"是两种一致性哲学，混做会两头不讨好（docs/04 有对比）。

### Q29. 大纲/翻页为什么是"连续滚动 + 大纲跳转"而不是 Word 式分页？
块编辑器的块高度是动态的（文本长度/类型/窗口宽度都会变），硬分页意味着每个协作操作
都可能引起全文重排（页码漂移对所有人广播），复杂度高且协作体验差；Notion/腾讯文档/
Google Docs 全部是连续滚动。长文档的定位诉求用大纲导航解决：h1-h3 实时生成、
点击平滑滚动、滚动高亮当前章节——这是"翻页"诉求在块编辑器范式下的正确答案。

### Q30. 悬停块右侧的 #seed / #xxxx 是什么？为什么要显示？
这是**块 ID 的前 4 位**（悬停显示完整 ID，点击复制）。块 ID 是整个协同系统的"地址"：
操作锚定（block.insert 的 afterId）、光标定位（cursor 消息的 blockId）、远程渲染
（按 data-id 找到对应 DOM 节点）、冲突检测（块级 CAS）、Undo（逆操作按 ID 反演）
全部以它寻址。显示出来是刻意的可观测性设计——演示"远程修改为什么能精确落在某一格"
时可以直接指着 ID 讲；调试时也能立刻对上"服务器日志里的块"和"屏幕上的段落"。
`#seed` 开头的是首次部署种子文档自带的 ID 前缀。

### Q31. 主题闪烁是怎么修的？为什么"瞬时切换"而不是更平滑的过渡？
闪烁有两个来源：(1) 主题类在入口 JS 执行时才加到 <html>，暗色用户首帧渲染的是白底
（FOUC，加载即闪一次）；(2) body/顶栏/编辑器各自带 0.2s 的 background 过渡，但边框、
阴影、color-mix 元素没有——切换瞬间一族元素渐变、另一族瞬变，不同步即闪烁。
修复：(1) 主题应用移进 index.html `<head>` 内联脚本，任何样式渲染前生效；
(2) 删掉全部颜色过渡，瞬时切换（业界主流做法）。教训：过渡动画只有"全部受影响属性
统一参与"时才成立，半吊子过渡比没有过渡更糟。

## v7 新增问题（八项完善的决策记录）

### Q32. 图片为什么存 data URL 而不是文件/对象存储？
面试体量下引入文件存储（磁盘目录/对象存储）会带来路径服务、清理任务、部署依赖三件事。
data URL 内联进块模型让图片天然享受整套协同管线（事务原子、幂等重发、快照、Undo、
diff 展示）。代价是每次同步携带 base64（带宽 ~33% 膨胀）与 SQLite 行变大——用两条护栏
对冲：客户端粘贴即压缩（长边 1280 + 迭代降质到 ~300K），服务器硬上限 300K 字符并校验
`data:image/` 前缀（防把任意文本塞进 src）。图片多了性能不够用时演进路线就是外部存储 +
URL 引用（Block.src 字段已就位）。

### Q33. 协作者名单为什么做成"enforce 开关的白名单"而不是独立访问模型？
独立模型（每人一个角色 + 邀请流 + 通知）要重写 hello 的角色判定与全部 REST 权限检查。
现有的"链接即凭据 + 仅创建者可编辑"加上一张白名单表（doc_collaborators），enforce 开启时
白名单内仍为 editor——三行代码就把语义从"只有我"变成"我和名单"，完全向后兼容。
这是增量演进的典型例子：先有粗粒度开关（v3），用户名单需求出现后升级为白名单（v7），
最后才是完整 ACL（未做，见不做清单）。

### Q34. 跨块选区的渲染为什么不做成"一个连续高亮"而按块分段？
每块是独立 DOM 子树，跨块的高亮只能是"每块内若干行矩形"的并集——我们按锚点块（到块尾）、
中间块（整块）、终点块（从头到 focus）三段各自求 Range.getClientRects()。另一个设计点：
消息里 blockId 恒为锚点、focusBlockId 恒为终点，**不做文档顺序归一化**——渲染按块独立
进行，顺序无关；比较两个 offset 的大小是无意义的（分属不同块），这正是 v7 修掉的 bug。

### Q35. E2E 为什么用 puppeteer-core 驱动本机 Chrome 而不是 Playwright？
零额外下载（不拉浏览器二进制，离线可跑）、复用开发者机器上已有的 Chrome/Edge。代价是
没有 Playwright 的自动等待生态——我们用 waitForFunction 轮询补足。E2E 断言选了
"最小完备集"（10 项）：覆盖双开同步、块类型、勾选、搜索、评论推送、只读、持久化——
每项都是手工回归里最容易坏、又最接近用户路径的路径。
