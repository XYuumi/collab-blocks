# 04 · 冲突处理与一致性

## 0. TL;DR

- 不用 OT/CRDT 作为正确性骨干，改用 **"文档版本 + 块级 CAS + 事务幂等 + 拒绝后自动重试"**；
- 不同块并发 → 永不冲突，双双生效；
- 同块并发 → 后到者被拒（Reject），客户端用**块内微型变换**把它的操作平移到新状态上，
  合并后**自动重试**（Retry）——双方输入都保留，收敛有自动化测试保证；
- 块锁（可选强制）把同块冲突从"事后仲裁"提前到"事前预防"。

## 1. 候选方案对比（思考过程）

### 1.1 写whole-doc / 整篇 Last-Write-Wins（LWW）
把整篇文档内容随每次保存全量提交，后写覆盖先写。
- 优点：实现 10 行。
- 致命缺点：A 改第一段、B 改最后一段同时提交 → B 覆盖 A，**A 的修改静默丢失**。
  对编辑器这是不可接受的：并发编辑是常态而非异常。

### 1.2 Document Lock（文档级编辑锁）
同一时刻只允许一个人编辑整篇文档。
- 优点：绝对无冲突，实现简单。
- 缺点：**并发度为 1**，"协同"名存实亡；锁等待体验差；锁持有者去倒杯咖啡全员阻塞。
  只适合强格式约束场景（如合同定稿），不适合常态化协同。

### 1.3 OT（Operational Transformation）
客户端发送字符级操作，服务器/对端把并发操作"变换"后应用（Google Docs 路线）。
- 优点：字符级并发合并，收敛严格证明（TP1/TP2）。
- 缺点：变换函数与不变量证明极其复杂（Google 花了多年）；中心服务器强依赖；
  调试困难。对本项目体量是杀鸡用牛刀，且题目明确问"如果不用怎么办"。

### 1.4 CRDT（Yjs / automerge 路线）
每个字符/位置是可复制数据类型，任意顺序合并都收敛。
- 优点：去中心化、离线编辑天然支持。
- 缺点：元数据开销大（每字符带 ID）、依赖成熟库（那就不是"自己实现"了）、
  一致性模型是"最终收敛"而非"服务器权威"（对文档场景，服务器权威更简单直接）。

### 1.5 本项目：Block 粒度的 CAS + Reject + 自动 Retry（+ 块内微型变换）
观察：**真实协同编辑中，两个人同时编辑同一个段落的概率远低于编辑不同段落**。
把冲突域缩小到块，绝大多数并发根本不构成冲突：

```
冲突判定（服务器，对事务中的每个 op）：
  block.blockVersion > tx.baseVersion 且 block.lastWriter ≠ tx.author
  └─ 该块在我所知的版本之后被"别人"改过 → 拒绝（CONFLICT）
  └─ 同作者豁免：自己的连续事务不冲突（本来就是顺序叠加的）
```

- **Version + CAS**：每块记录"最后被修改时的文档版本"，把乐观并发控制
  （Compare-And-Swap）从文档级细化到块级；
- **Reject 而非 LWW/FWW**：被拒的事务不会丢——客户端知道确切原因并持有自己的 ops，
  可以基于服务器权威状态**重建后重试**。LWW/FWW 都会静默丢数据，Reject 把决策权
  交回拥有最多信息的客户端；
- **Retry 的正确性**：重试前客户端先把 pending ops"平移"到服务器新状态上
  （块内微型变换 + clamp + 重锚），平移后的 ops 与服务器状态一致，重试成功即收敛。

## 2. 场景矩阵

| 场景 | 结果 | 最终内容 |
|---|---|---|
| A、B 同时改**不同块** | 双方都成功（块级 CAS 放行） | 两处修改都保留 |
| A、B 同时改**同块不同位置**（无提交交错） | 后台自动合并 | 微型变换平移后双方输入都保留 |
| A、B 同时改**同块**且 A 先提交 | B 的在途事务被拒 | B 自动变换重试成功 → 双方输入都保留（测试：client/test/model.test.ts "同块并发"） |
| B 离线编辑期间 A 改了同一块 | 重连对账重放时 B 的 ops 被服务器 CAS 拒 | B 走修复管线：以 A 的结果为基底重放合并，双方输入保留 |
| A 删除块 X，B 同时编辑块 X | A 成功；B 的事务发现目标块不存在 | B 的编辑被丢弃（目标已不存在），Toast 告知；这是"删除优先"的语义选择 |
| A 删除块 X，B 同时在 X 后插入新块 | 双方成功 | B 的插入锚点失效 → 服务器宽松重锚到末尾，客户端同步重锚，两端块序一致（有测试） |
| 强制锁下 B 写 A 持锁的块 | 服务器 nack LOCKED | B 的写入被回滚丢弃（前端已置只读，这是竞态兜底） |
| 同一事务重复到达（重发/重连） | 幂等去重 | 只执行一次，版本不重复增长 |

## 3. 块内微型变换（介于"纯 Reject"与"完整 OT"之间）

服务器拒绝只解决"谁先落地"；要让**后到者的输入不丢**，客户端在收到同块远程 op 时，
把自己 pending 中的文本 op 做单边平移（`client/src/util.ts: transformTextOp`）：

```
我的 insert(offset)  vs 远程 insert(ro, len)：offset ≥ ro → offset += len
我的 delete(s,e)     vs 远程 insert：区间包含插入点 → 删除区间扩大
我的 insert(offset)  vs 远程 delete(rs,re)：offset 在被删区间内 → 移到 rs
我的 delete(s,e)     vs 远程 delete：区间相减收缩
```

**这是近似的单边变换，不是 OT**：
- 只覆盖 insert/delete 两类 op（本项目的全部文本 op），没有 tombstone/无字符 ID；
- 平局规则是确定性的：并发同位置插入，**后提交者排在先提交者之后**（`ABhello` 测试）；
- 不追求"任意拓扑下都符合直觉"，只追求：**平移后的 ops 重放到服务器状态上，结果与
  服务器将来应用这些 ops 的结果一致**——即"本地看到的合并结果 == 服务器最终结果"。
  这由"ack 时 serverText 恰为发送 ops 的应用基底"（块级 CAS 保证无他人写入穿插）
  这条不变量支撑，收敛性由 `client/test/model.test.ts` 的双模型测试验证。

## 4. 收敛性论证（为什么敢说收敛）

设块 B 上：服务器版本 v0 时文本为 S0。
1. 任何提交到服务器的 op 序列都被**串行**应用（单线程事件循环 + 原子副本交换），
   服务器状态是全序的、确定的；
2. 客户端可见文本 ≡ `fold(pending 文本 ops, serverText)`（折叠等价，模型维护）；
3. 客户端 serverText 只经 ack/remote.op/snapshot 推进，且值来自服务器
   （同连接内有序）→ serverText ≡ 服务器某历史版本的块状态；
4. 我的 tx 被 ack ⟹ 服务器在应用我的 ops 之前，B 的最后写入者是我
   （否则被 CAS 拒绝）⟹ 应用基底 == 我的 serverText ⟹ 服务器结果 == 我的折叠结果；
5. 我的 tx 被 nack ⟹ 修复管线把我重置到服务器权威状态再重放 → 回到情形 4 或被再次
   拒绝（继续重试，服务器状态有限推进，最终成功或 op 被丢弃——两种都可收敛）。

因此：**每个客户端的可见文本最终等于服务器块文本**（快照对账兜底任何累积误差）。

## 5. 如果要用 OT/CRDT，演进路线

- **OT**：把 `transformTextOp` 换成完整双边变换（T(o, p) 与 T(p, o)），服务器维护
  历史操作做客户端变换回放；块结构 op 需要单独的变换族。工作量主要在变换函数的
  正确性证明与测试。
- **CRDT**：Block 层改用 RGA/List CRDT（块 ID + 左邻居），文本层用 YATA 或直接
  引入 Yjs；服务器退化为中继 + 持久化，权威性让位于最终一致；离线编辑时间不再受限。
- 本项目结构的预留：Op 是封闭集合、模型层是纯函数、服务器仲裁集中在 DocEngine——
  替换任何一层不影响其他层。

## 6. 已知限制（如实说明）

1. **撤销不感知他人编辑**：本地线性撤销（逆 op 事务），撞上他人的同块修改会被
   CAS 拒绝或位置偏移（有 clamp 兜底不越界）。跨用户撤销的正确做法是
   selective undo（基于 op 依赖图），超出本项目范围。
2. **微型变换的近似性**：极端交叠场景（如两人同时在完全相同位置删除重叠区间并插入）
   的合并结果可能不符合任一方的直觉，但仍然收敛、不丢非冲突内容。
3. **同事务跨块的部分成功不会发生**（原子），但"重连重放时某个 op 的目标块消失"
   会丢弃该 op（Toast 告知）——选择显式丢弃而非静默保留，避免幽灵内容。
4. **服务器单点**：单进程内存态 + 文件持久化；水平扩展需要引入 Redis 广播 /
   文档分片，未实现。
